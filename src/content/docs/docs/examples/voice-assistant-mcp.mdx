The [headline voice assistant](/docs/examples/voice-assistant/) declares a single inline tool and wires it to a GPIO pin. That works when *you* own the action. When the action lives behind a tool surface someone else maintains — a Home Assistant bridge, a notes daemon, a CLI wrapper, anything that speaks the [Model Context Protocol](https://modelcontextprotocol.io/) — bridging it into the bot is one line.

`assistant.create({ tools })` accepts a structural type with `.tools: ToolDescriptor[]` and `.call(name, args)`. `@para/mcp` connection objects fit that shape natively, so dropping a connection into `tools: [...]` flattens every tool the server exposes into the bot's catalog. The grammar-constrained generation, JSON dispatch, and round-tripped result are identical to inline tools.

## src/agent.pts

```parabun
import assistant from "parabun:assistant";
import mcp       from "@para/mcp";

// Spawn the MCP server as a subprocess and speak JSON-RPC over its stdin/stdout.
// Replace the command with whatever MCP server you want to bridge.
await using home = await mcp.connect("stdio", "home-assistant-mcp", {
  args: ["--config", "/etc/home-assistant/mcp.toml"],
  env: { ...process.env, HASS_TOKEN: process.env.HASS_TOKEN },
});

await using bot = await assistant.create({
  llm: process.env.ASSISTANT_LLM,
  stt: process.env.ASSISTANT_STT,
  tts: process.env.ASSISTANT_TTS,
  system: "You are a concise smart-home assistant. Use tools to act.",
  tools: [home],                        // ← every home.* tool is now reachable
});

// Live status line, plus a count of how many tools are available.
derived header = `\r[${bot.state.get().padEnd(10)}] (${bot.tools.length} tools)`;
header -> process.stdout.write;

await bot.run();
```

## What this gets you

- **`home.tools`** is populated during the `initialize` handshake — the bot snapshots it and includes every entry in the JSON-schema-constrained generation grammar. Tool-call requests route through `home.call(name, args)`; the JSON result is fed back to the model so the spoken response reflects what actually happened.
- **`home.alive`** is a `Signal<boolean>` — false when the subprocess exits or the WebSocket drops. Bind it to a status indicator or wrap your bot's `run()` in `effect { if (home.alive.get()) … }` for auto-reconnect.
- **`bot.tools`** is the flattened catalog (inline + MCP). Each entry carries `source: "inline" | "mcp"` so a UI can render where each came from.

## Mixing inline and MCP tools

`tools: [...]` accepts the union — inline descriptors and MCP connections side by side. The headline GPIO example becomes:

```parabun
await using chip = await gpio.openDefaultChip();
await using led  = chip.line(17, { mode: "out", initial: 0 });

await using bot = await assistant.create({
  llm, stt, tts,
  tools: [
    home,                                                                    // every MCP tool
    {
      name: "setLight",
      description: "Toggle the local LED wired to BCM 17.",
      schema: { type: "object", properties: { on: { type: "boolean" } }, required: ["on"] },
      run: ({ on }) => { led.write(on ? 1 : 0); return `local LED ${on ? "on" : "off"}`; },
    },
  ],
});
```

The bot sees one merged catalog; the LLM picks among them at each turn.

## WebSocket transport

`mcp.connect("ws", url)` is the same surface for servers that speak MCP over a WebSocket text frame:

```parabun
await using hub = await mcp.connect("ws", "ws://hub.local:8080/mcp", {
  headers: { authorization: `Bearer ${process.env.HUB_TOKEN}` },
});
```

Either transport works in `tools: [...]`.

## Run it

```bash
ASSISTANT_LLM=$HOME/models/Llama-3.2-1B-Instruct-Q4_K_M.gguf \
ASSISTANT_STT=$HOME/models/ggml-tiny.en.bin \
ASSISTANT_TTS=$HOME/models/en_US-lessac-medium.onnx \
HASS_TOKEN=… \
  parabun src/agent.pts
```

The status line will show `(N tools)` once the MCP handshake completes; speak after `[listening ]` shows up. The LLM is constrained to call one of those N tools or reply in plain text — no malformed JSON, no hallucinated tool names.

## Hardware

Same as the [headline voice assistant](/docs/examples/voice-assistant/#hardware) — Linux + ALSA, NVIDIA GPU for the LLM, mic + speakers. The MCP server runs wherever it normally runs (subprocess, daemon, websocket endpoint); the bot doesn't care.
